## Approved bounded implementation now implemented

Activation is explicit `-SoulSettlementDevelopmentProof`. The fixed scenario path is `/Game/Soul/Data/Settlements/DA_Soul_HumanCapital_DevelopmentProof`. Missing/invalid data leaves a requested-but-unready proof, with an error getter; construction and hiring fail closed. Root's GameMode/qualification layer must report this and reject the proof, rather than silently displaying the old capital. Ordinary play without the flag retains knight recruitment and tavern-hire behavior.

1. `USoulSettlementScenarioData` now has reflected `FSoulBuildingDevelopmentSpec` entries: `BuildingId`, `Category`, `MaxLevel`, `BuildDays`, `BuildCost`, `Prerequisites`, `UnlockIds`. `ToDefinition()` supplies the existing Core struct. `ValidateDefinition()` rejects missing/duplicate ids, nonpositive duration/maximum level, negative costs, missing/self/repeated/cyclic prerequisites, invalid seed levels/integrity and invalid unlock ids. An optional `OwnedEnvironmentMap` soft `UWorld` reference is presentation data; it cannot change ownership or legal encounters.
2. `USoulSettlementStateSubsystem::EnsureScenario(Scenario, Error, bOnlyCreateIfMissing=true)` validates before mutation, then seeds only absence. `ASoulSettlementBootstrapActor` delegates to it. It never creates a second authority.
3. Founder `InitializeSettlementDevelopment(Scenario, Authority, Error)` requires the existing same-GameInstance settlement authority, the existing Human Capital region and faction, and the tavern definition with `service.tavern_hero`. This service token binds the existing `HireTavernHero` action; it adds no new hero system. A mismatched saved region fails with state preserved.
4. Founder `BeginSettlementConstruction(BuildingId, Error)` enforces current region, campaign ownership, settlement ownership, definition membership, no pending battle and no persistence operation, then invokes `FSoulTownRules::BeginConstruction`. Failure does not spend; duplicate purchase fails. `AdvanceDay` advances the original economy once and construction once. The existing knight pool remains unchanged.
5. `IsTavernOperational()` derives service access through the same definition and `FSoulSettlementRules::IsOperational`. The existing hire price and `bSecondHeroHired` save field are unchanged. Root has approved provisional proof data of 200 gold / two days; this is not full balance acceptance.
6. On successful campaign load, an entirely absent legacy town may be seeded from the opt-in scenario; existing town progress is never reset. Initial binding and the actual F9 callback now share immutable region/faction/campaign-owner validation. A mismatched restored town is preserved, the proof becomes unready and day advancement is blocked; loading a valid checkpoint later clears that error. `SettlementDevelopmentRevision` is transient presentation invalidation only. Save schemas and selected domains are unchanged.

Public API for root-owned UI/presentation:

```cpp
bool IsSettlementDevelopmentEnabled() const; // requested, including unready
bool IsSettlementDevelopmentReady() const;
const USoulSettlementScenarioData* GetSettlementScenario() const;
const FString& GetSettlementDevelopmentError() const;
bool BeginSettlementConstruction(FName BuildingId, FString& OutError);
bool IsTavernOperational() const;
uint32 SettlementDevelopmentRevision; // transient, observe with CampaignLoadRevision
```

Campaign and visit UI now invoke the same founder command. With the proof active, the town panel adds U/build and V/visit, data-derived cost/duration/progress and the existing service gate. The visit reuses the existing Founder controller/HUD for build, day, hire, F5/save, F9/load and Escape/return. `ASoulSettlementVisitGameMode::CanVisit` requires readiness, current owned settlement, no pending battle/save operation and an existing map under `/Game/Soul/`. It uses the scenario soft world binding and returns through the existing campaign map binding. BeginPlay verifies the exact package (with PIE prefix removed), waits up to 20 seconds for the authored `SoulTownViewAnchor`, and fails visibly if absent. Return remains available. No environment is synthesized when the map is missing.

The visit refreshes existing matching presentation controllers on development/load revision changes and once its anchor is ready. The campaign miniature binding remains root-owned and pending genuine assets. Groups that are LevelInstances need an actual runtime check of loaded children, visibility and collision. The generic external actor group helper enables collision for the visible group; keep miniature meshes noninteractive through their component collision settings, and qualify visit collision separately.

## Battle and map boundary

`Source/SoulCore/Public/SoulCampaignBattleBridge.h:8` explicitly makes the bridge transport-only. `FSoulCampaignBattleDescriptor::IsValid` (`SoulCampaignBattleBridge.cpp:3`) accepts only the installed human-knight/dwarf-warrior matchup. Founder `BuildBattleDescriptor` still derives the battlefield recipe from a legal adjacent hostile destination; `StartBattle` (`SoulFounderPlaytestCampaignActor.cpp:297`) opens its admitted map with the realtime GameMode. Realtime `SoulRealtimeBattleArena.cpp:1170` validates the loaded map against the descriptor, and `:4125` validates/resolves the result before returning to campaign.

Both state subsystems live in the GameInstance and survive `OpenLevel`. Consequently, an authored environment presenter can read the same settlement state after a visit or battle map load without copying it into the descriptor. The passing native test proves that a valid existing hostile-edge result does not replace development state and that the combined save restores it into a fresh GameInstance. It does **not** prove runtime travel or combat in the capital.

For the actual environment battle proof, use a separately explicit qualification admission of the owned environment at the existing validated battle transport boundary, with safe arena/deployment/collision evidence. Do not change friendly Crownstead ownership or forge a legal attack on it. Do not substitute `human_capital` for the canonical hostile target. The exact authored map, read-only settlement binding and encounter receipt must distinguish environment presentation from the canonical attacked region. No bridge/combat edits were made by this work.
